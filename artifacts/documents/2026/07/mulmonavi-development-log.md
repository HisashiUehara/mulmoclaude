# MulmoNavi 開発ドキュメント — 開発の流れと経緯

作成日: 2026-07-16
対象: 音声カーナビアプリ **MulmoNavi**（本体 `artifacts/html/2026/07/voice-nav.html` ＋ コレクション `data/skills/voice-nav/`）

---

## 0. このドキュメントについて

本書は、MulmoNavi を一連の対話を通じて作り上げていった**開発の全記録**です。あなた（ユーザー）が出した要望・判断・フィードバックと、それに対して行われた調査・実装・検証を、時系列で振り返ります。単なる機能一覧ではなく「**なぜその変更に至ったか（経緯）**」を残すことを目的としています。

---

## 1. 出発点

- 起点は既存のスキル **`voice-nav`**（当時の名称「音声ナビ」）。Google Maps ＋ Web Speech API（音声認識 STT / 音声合成 TTS）で動く、ブラウザ完結のカーナビ Web アプリでした。
- 「男体山（nantai-san）」が保存済みの行き先として登録されており、そこから対話がスタート。
- この時点のアプリは **パターンマッチ＋定型文辞書**で動く仕組み。「◯◯まで」で目的地検索 → ルート構築 → ターンバイターン案内、というシンプルな構造でした。

あなたの最初の関わり方は「既にあるものを、実際に使いながら細かく直していく」というスタイルで、これが最後まで一貫していました。

## 2. フェーズ1 — UI/文言の磨き込み（対話の質を上げる下地）

実際に触りながら、気になった点を1つずつ指摘して直していきました。

1. **例文プレースホルダーの削除**
   「例：東京駅まで、近くのコンビニ」のような例示を、あなたは「最小限の文言でいい」と判断。あいさつ文・応答文から例示を全削除。

2. **目的地確認「はい／違う」の廃止**
   候補が複数あるとき「候補は3件あります。はい／違う」と聞く挙動を、あなたは不要と判断。**確認ステップを廃止し、先頭候補を即採用**する方式に変更。

3. **高速道路（有料道路）を使うかの確認を追加**
   逆に、ここは**確認を足す**判断。目的地設定後に「高速道路を使いますか？」と尋ね、返答で `avoidTolls` / `avoidHighways` を切り替える仕組みを実装。徒歩モードでは高速に無関係なので確認しない、という細かい配慮も入れました。

4. **アプリ名の変更（音声ナビ → MulmoNavi）**
   本体・ランチャー・コレクション定義まで、表示名を横断的に統一。

5. **保存済み行き先の削除**
   「男体山」「東京駅」を全削除し、コレクションを空に。

6. **括弧書き（…）を音声に読ませない**（重要な気づき）
   スクリーンショット付きで「（使う／違う）のような括弧を音声がそのまま読み上げてしまい、長ったらしくて煩わしい」と指摘。ここであなたは**単発の修正でなく恒久ルール**を求めました。対応は3段構え:
   - 該当文言から括弧を削除
   - 読み上げ関数 `tts()` に `stripParens()` を入れ、**発話直前に括弧内を常に除去**
   - 「読み上げを伴う文に括弧書きを入れない」を**好みとしてメモリに保存**（以後の開発方針に反映）

この「その場しのぎでなく仕組みで直す」という要求は、以降の開発全体を貫くテーマになりました。

## 3. フェーズ2 — スマホ対応

- あなたは「スマホからもアクセスできるように」と要望。
- 当初は配信方法（公開HTTPS / LAN / PWA 化）の選択肢を提示しましたが、あなたが状況を明確化: 「**MulmoClaude にリモート端末としてスマホは接続済み。だが MulmoNavi のページを開くと UI が出ず "No records" だけ**」。
- 原因は、ランチャービューが**デスクトップ用のカスタムビュー**だったため、スマホのリモートアプリ（別の描画契約・`target:"mobile"`）では表示されなかったこと。
- 対応: **スマホ専用のカスタムビュー `phone.html`（`target:"mobile"`）を新規作成**。ただしスマホのリモートビューはサンドボックスで Google Maps を読み込めないため、**Google マップアプリのディープリンク**方式を採用。行き先をタップすると `https://www.google.com/maps/dir/?api=1&destination=…` でスマホのネイティブ Google マップが起動し、そのまま案内が始まる設計にしました。

## 4. フェーズ3 — 会話が成立しない問題と、LLM 化への布石

### 4-1. 「挨拶したら高速道路の質問が返る」バグ
- あなたの報告: 「こんにちは」と話しかけたのに「高速道路を使いますか」と返り、会話が成立しない。
- 調査で判明した根本原因: 挨拶判定が**完全一致（`^こんにちは$`）**のみで、「はいこんにちは」のように**先頭に相づちが付いた挨拶**や音声認識で語が繋がった挨拶が判定を外れ、**目的地クエリとして扱われてジオコードされていた**（＝勝手に目的地化）。
- さらに調査中に、以前追加された正規表現に **`\b?` という無効な記述**（V8 でも例外→スクリプト全停止）を発見・修正。
- 対応: フィラー除去後の変種でも挨拶/お礼/雑談を判定するように改善。

### 4-2. 「このアプリの構造を教えて」
- ここであなたは一度立ち止まり、アプリ全体の構造（UIレイヤー / 状態管理 / i18n / TTS / STT / 意図解析 / ルート構築 / ターンバイターン案内）の説明を求めました。全体像を把握した上で次の大きな一手に進む、という流れ。

### 4-3. 会話の LLM 化（ハイブリッド2層）— 調査を最優先にする指示
あなたは明確な進め方を指定しました:
- 「**実装より先に調査**。新設する `/api/nav-chat` の LLM バックエンドに何が使えるかホスト側を調べて報告して。Claude を Max 認証のまま使えるか、無理なら OpenAI か。**キー課金の判断は私がする**ので、そこで止まれ」
- 調査結果:
  - **Claude CLI**（`--print` モード）は**サブスク認証のまま API キー不要**で短文応答に再利用可能。ただし**実測で 1ターン 5.7〜11.5 秒**とカーナビ会話には遅すぎる。
  - **OpenAI gpt-4o-mini** は `.env` の既存キー流用・低遅延。
- あなたの判断: **OpenAI gpt-4o-mini を採用**（速度優先。キーは既存で新規発行不要）。加えて「スマホでも LLM 会話したい」も表明（後段の配信課題として記録）。
- 設計: **2層ルーティング**
  - 第1層（遅延ゼロ・パターンマッチ維持）: stop/start/repeat/mode/category/高速確認 など
  - 第2層（新設）: 第1層で分類できない発話を `/api/nav-chat` に委譲
- 実装は段階的に、各段で止まって報告する方針を徹底:
  - **フェーズ2: `/api/nav-chat` 単体** — TTS と同じ view-token パターン（専用スコープ `aud:"nav-chat"`・TTL 1h・レート制限20/分・入力300字）、システムプロンプト固定、OpenAI chat completions プロキシ。curl テストで 401/400/雑談/ETA参照/アクションJSON を実証。
  - **フェーズ3: クライアント統合** — 第2層ルーティング、few-shot、応答待ちの「えっと」フィラー、API失敗時は定型文フォールバック、走行コンテキスト注入。あなたの追加指定で「few-shot は最小3例」「フィラーは800ms以内に返れば挟まない」「動作確認手順を含める」を反映。

## 5. フェーズ4 — OpenAI 音声（TTS）

- あなたは「中断していた OpenAI TTS 実装を再開。nav-chat で確立した認可基盤に乗せる」と指示。
- 調査で判明: **`/api/tts` は過去に構築済みだが未使用**のまま眠っていた（view-token・レート制限・503フォールバックまで配線済み）。新規実装は不要でした。
- クライアント側を **3段構え**で実装:
  1. ナビ定型文 → 初回生成後 **IndexedDB にキャッシュ**（走行中ゼロ遅延）
  2. nav-chat の会話応答 → リアルタイム生成
  3. `/api/tts` 不達・キー未設定時 → **Web Speech へ自動フォールバック**（ナビは絶対に壊れない）
- ⚙️設定に「OpenAI TTS を使う」トグル（あなたの選択で**初期ON**）＋ボイス選択（**nova**）。
- nav-chat 応答受信と同時に TTS 生成を開始し、再生開始までの合計遅延をログ出力。

## 6. フェーズ5 — 「声が変わらない」トークン到達問題との長い戦い（本開発最大の難所）

ここからが、繰り返し現れて何度も対策した**中心的な経緯**です。

### 6-1. 「滑らかじゃない、本当に OpenAI 使ってる?」
- あなたの疑い: 音声が英語訛りで滑らかでない。本当に OpenAI か。
- 対応: **どのエンジンで鳴ったかを画面バッジで可視化**（OpenAI / OpenAI⚡キャッシュ / 内蔵）。あわせて音質を `tts-1-hd` に。正直な補足として「日本語では OpenAI tts-1 より Chrome の Google 日本語音声の方が自然なこともある」ことも伝えました。

### 6-2. モデル/ボイス変更（tts-1-hd / shimmer）
- あなたの指示で既定モデルを `tts-1-hd`、既定ボイスを `shimmer` に。キャッシュキーに model/voice を含め、切替時の旧音声混入を防止。tts-1 比の遅延増（+約128ms）も実測して報告。

### 6-3. 「変えたのに声が全く変わらない」→ 徹底調査
- あなたは「TTS が音声経路に到達していない疑い」を立て、**5段階の調査手順を具体的に指定**（実際に鳴っている経路の特定、トークン受け渡し検証、トグル/移行フラグ検証、`/api/tts` 単体の生存確認、遅延内訳分解）。「**Web Speech が鳴っていたと判明したら根本原因と修正案を提示して止まれ**」と、切り分けの順序まで指示。
- 調査で確定:
  - **サーバーの `/api/tts` は完全に正常**（gpt-4o-mini-tts で 200・有効MP3）。
  - **クライアントが `/api/tts` に到達できず Web Speech にフォールバック**していた。
  - あなたが実機の `DIAG` ログ（`hashHadMcvt:false / hasTtsToken:false / origin:localhost:5173`）を貼ってくれたことで、**トークンがアプリに渡っていない**と一意に確定。
- 修正（あなたの指示で4点）:
  1. ランチャーの mint 完了までボタンを無効化（**mintsReady ゲート**・レース対策）
  2. トークン未受領時に画面へ案内表示（ランチャーから開き直す導線）
  3. `/artifacts` 配信に `Cache-Control: no-cache`（旧HTMLキャッシュ事故の予防）
  4. `TEMP-DIAG` ログは動作確認まで残置

### 6-4. CSP で blob: がブロック
- 音声再生（`blob:` URL）が `default-src 'none'` で弾かれる問題。あなたは「サーバー側で `/artifacts/html` の CSP に `media-src blob:` を追加、または CSP 適合の再生方式に」と指示。
- 対応: CSP ビルダーに `mediaSrc` 引数を追加し、**この配信文書だけに `media-src blob: data:` を付与**（`connect-src 'self'` と同じスコープ方式・print/srcdoc はロック維持）。

### 6-5. フィラー廃止・診断ログ削除
- あなたの判断で「えっと」フィラーを廃止（応答待ちは無音でよい）。TEMP-DIAG も削除。

## 7. フェーズ6 — 多言語の一貫化

- あなたの指摘: 「男体山まで」で読み上げが「目的地を『Mount Nantai（Mount…』」と**日英混在**する。🌐切替が一部にしか効いていない。
- 根本原因: **Google Maps を言語指定なしでロード**しており、地名・住所が英語で返っていた。地名の言語は Maps ロード時の `language` で決まり、実行時に変えられない。
- 対応:
  - Maps ローダに `language` / `region` を `S.lang` から付与。
  - 🌐切替を「永続化＋リロード」に変更（Maps を新言語で読み直し、UI・案内・検索・TTS・会話・音声認識をすべて追従）。
  - nav-chat の context に `lang` を追加、システムプロンプトに「必ず context.lang の言語で・混在禁止」を明記。
- 検証: 日本語モードは全て日本語、英語モードは全て英語（curl でLLM応答の言語一貫を実証）。

## 8. フェーズ7 — 日本語音声品質の追い込み

- あなたの指摘: OpenAI TTS の日本語が英語訛りで流暢でない。改善して。指示は3本立て:
  1. まず調査（`instructions` 等の言語ヒントを渡しているか）
  2. **全9ボイスの日本語聴き比べ**を用意して自分で最良ボイスを選べるように
  3. `gpt-4o-mini-tts` の `instructions` で「日本語ネイティブの発音」を指定できるか、可能なら選択肢に
  4. 言語モードに応じたボイス自動切替
- 調査結果: `/api/tts` は言語ヒント未送。`tts-1-hd` は `instructions` 非対応。**`gpt-4o-mini-tts` は `instructions` 対応**。
- 対応:
  - 全9ボイス（gpt-4o-mini-tts＋日本語指示）＋参考の聴き比べを**自己完結HTML（data:音声）**で生成・提示。
  - サーバー `/api/tts` に `instructions` パラメータを追加（対応モデルにのみ転送し、tts-1系への誤送で400を防止）。
  - クライアントを**モデル選択＋言語別ボイス（自動切替）**に拡張。既定を `gpt-4o-mini-tts` に。

## 9. フェーズ8 — バグ退治（二重発火・遅延・音の重なり）

### 9-1. 二重発火（1発話で nav-chat が2回・二重課金）
- あなたはログの証拠（net=3736ms と 3742ms の2本、異なる返答）を添えて報告。
- 根本原因（2つ）:
  - 音声認識 `onresult` が `results[length-1]` を毎回読み、continuous 認識で同一 final に複数回発火。
  - 破棄済み recognizer が `onresult` を残したまま `stop()` され、バッファされた final が漏れて2回目発火。
- 修正: result index ベースで「各 final を一度だけ処理」、`killRecog()` で全ハンドラを null にしてから停止、加えて **handleInput に同一発話1.5秒ドロップの保証ガード**。

### 9-2. 遅延の悪化（合計10秒）
- あなたは内訳分解を要求。実測で判明した重要事実:
  - nav-chat は典型 0.8〜1.4秒（3.7秒はコールドのスパイク）。`max_tokens` 80→40 で約-500ms。
  - **`gpt-4o-mini-tts` は tts-1-hd より速い**（full 1.6秒 vs 4.5秒）。「6.3秒」は旧デフォルト tts-1-hd の症状で、モデル切替で解消。
  - ストリーミング化は gpt-4o-mini-tts なら不要（目標3秒以内に収まる）。
- あなたの判断: **①再起動で gpt-4o-mini-tts 有効化 ＋ ②max_tokens 48** の両方で進め、**ストリーミングは見送り**、システムプロンプト短縮は保留（会話品質を守る）。

### 9-3. 「同時に AI が喋る」
- 症状: 二重発火とは別の**再生の重なり**。
- 根本原因: `tts()` が非同期で、割り込み `stopSpeaking()` は開始時に呼ばれるが実再生は約1.6秒後。2発話がほぼ同時に来ると両方が生成完了後に再生され重なる。
- 修正: **TTS を直列キュー化**（1つ再生し終えてから次）。`playBlob` を「再生終了」で解決するよう変更、`webSpeak` も await 可能化、新しいユーザー発話で `flushTts()`。

## 10. フェーズ9 — 会話の自然さ（設計の既定を反転）

- あなたの根本的な不満: 「目的地が勝手に変わる」「自然な会話ができない」。
- 根本原因（設計）: `parseIntent` の**既定の落とし先が「地名検索（ジオコード）」**。挨拶以外で文字が残る発話はすべて行き先として検索され、勝手に目的地化していた（例:「今日は疲れたなあ」→ 適当な地点）。
- 修正（既定を反転）:
  - **明示的な行き先マーカー**（「〜まで」「〜へ」「案内して」「go to」等）がある時だけ直接ジオコード。
  - それ以外はすべて **nav-chat（LLM）に委譲**。LLM が雑談なら会話で返し、地名なら `set_destination` を返す。
  - サーバープロンプトに「地名だけなら set_destination／感情・質問・雑談は会話・**勝手に目的地を作らない**」を明記＋例追加。
- 検証: 「東京駅」「スカイツリー」→ set_destination、「疲れた」「いい天気」「元気?」→ 会話。地名は行き先に、雑談は会話に、正しく分離。

## 11. フェーズ10 — トークン自己取得 ＆ バージイン（会話の完成）

繰り返し現れたトークン到達問題に、ここで**恒久的な決着**をつけました。

- あなたの要望: 「会話にならない。会話ができるように。あと**私が AI の声に割り込んで話せる**ように」。
- **①会話の恒久対策（トークン自己取得）**
  - 主因は依然として「トークンがアプリに届かず nav-chat が定型文に落ちる」こと（ランチャーのフラグメント受け渡しが不安定）。
  - 新エンドポイント **`POST /api/nav-view-tokens`** を追加。**same-origin（ループバック）ガードのみ**で bearer 不要にし、**アプリが起動時に自分で tts / nav-chat トークンを取得**する方式に。ランチャー依存を排除。
  - 検証: 自己取得→両トークン発行→nav-chat/tts とも200、別audienceトークンは401（スコープ分離維持）。
- **②バージイン（割り込み発話）**
  - これまでエコー防止で AI 発話中はマイクを無視していた。
  - AI 発話中も認識を継続し、**自分の TTS のエコーか判定（`isEcho`）**。エコーは無視、ユーザーの発話なら `flushTts()` で AI を即停止して処理。
  - これで AI が喋っている最中でも話しかければ AI が止まり、ユーザーの発言に切り替わる。

## 12. 最終アーキテクチャ（到達点）

```
[音声🎤 / テキスト]
   │
   ▼
handleInput（二重発火ガード → flushTts で割り込み）
   │
   ▼
第1層 parseIntent（遅延ゼロ・確定的）
   ├ stop / start / repeat / mode / category / 高速確認
   ├ 明示的な行き先マーカー有り → searchDestination（ジオコード）
   └ それ以外 → 第2層へ
        │
        ▼
   /api/nav-chat（OpenAI gpt-4o-mini・view-token 認可・context注入）
        ├ {reply} → 会話（自然な相棒応答）
        └ {action} → set_destination / add_waypoint / stop / start / repeat / play_music

読み上げ（直列キュー）:
  tts() → pumpTts()（1件ずつ）→ speakOne()
     ├ OpenAI TTS（gpt-4o-mini-tts・言語別ボイス・instructions）→ IDBキャッシュ
```
