# 音声カーナビ「MulmoNavi」を対話だけで作り込んだ全記録 — 各フェーズ詳細

> 既存の素朴な音声ナビを、実際に使いながら少しずつ直し、最終的に「LLMと自然に会話でき、割り込んで話せて、日本語でも滑らかに喋る」カーナビへ育て上げるまでの開発日誌。対症療法ではなく、毎回**根本原因**に手を入れていった記録です。

---

## はじめに — 何を作ったか

MulmoNavi は、ブラウザ完結の音声カーナビ Web アプリです。

- 本体: 1枚の HTML（`voice-nav.html`）。Google Maps ＋ Web Speech API（音声認識/合成）で動く。
- 「◯◯まで案内して」で目的地検索 → ルート → ターンバイターン読み上げ。
- 雑談も成立する（OpenAI の LLM で会話）。地名を言えば行き先に、雑談には会話で返す。
- 音声は OpenAI TTS（gpt-4o-mini-tts）で、日本語も自然。定型文はキャッシュして走行中ゼロ遅延。
- AI が喋っている途中でも、こちらが話しかければ止まって聞く（バージイン）。

出発点は、パターンマッチと定型文辞書だけで動く素朴なアプリでした。そこから 10 フェーズかけて、ここまで持っていきました。以下、各フェーズを実際の作業ベースで詳細に書きます。

## フェーズ1 — UI と文言の磨き込み

「まず触って、気になるところを潰す」から始まりました。地味ですが、後の会話品質の土台になった重要な工程です。

### 1-1. 例文プレースホルダーを消す
「例：東京駅まで／近くのコンビニ」のような例示を、あいさつ文・応答文・チャット案内から全削除。i18n 辞書（`I18N.ja` / `I18N.en`）の該当文字列を短くしました。

### 1-2. 目的地確認「はい／違う」を廃止
元は候補が複数あると「候補は3件あります。はい／違う」と聞いていました。これを廃止し、`presentCandidates()` を「先頭候補をそのまま `setDestinationCandidate()` に渡す」形に変更。確認フロー（`offerCandidate` / `confirmCandidate` / `nextCandidate`）を実質バイパスしました。

### 1-3. 逆に「高速道路を使うか」の確認は足す
削るだけでなく、必要な確認は追加。状態オブジェクト `S` に `avoidTolls` / `avoidHighways` / `pendingRoad` を追加し、目的地設定後（車モードのみ）に「高速道路を使いますか？」と尋ねる。返答は専用の `classifyRoad()` で判定し、Google Directions の `avoidTolls` / `avoidHighways` に反映。徒歩モードでは高速に無関係なので確認しない、という分岐も入れました。

### 1-4. アプリ名を「音声ナビ」→「MulmoNavi」へ
本体（`<title>`・ヘッダー・i18n の `title`・読み上げの自己紹介文）だけでなく、ランチャー（`launcher.html`）の見出し・起動ボタン、コレクション定義（`schema.json` の `title` とビューの `label`）まで横断的に統一。

### 1-5. 括弧書き（…）を音声に読ませない（この工程の白眉）
「（使う／違う）のような括弧を音声がそのまま読み上げてしまい、長ったらしい」という指摘。ここで単発修正ではなく**恒久対策**を選んだのがポイントでした。

- 該当文言から括弧を削除。
- 読み上げ関数 `tts()` に `stripParens()` を追加し、**発話直前に全角/半角の括弧と中身を常に除去**（`/[（(][^（()）]*[）)]/g`）。画面表示はそのまま、音声だけ除去。
- 「読み上げを伴う文に括弧書きを入れない」を**好みとしてメモリに保存**し、以後の開発方針に固定。

この「仕組みで直す」姿勢が、以降ずっと効いてきます。

## フェーズ2 — スマホ対応

「スマホからも使いたい」から出発。最初は配信方法（公開HTTPS / LAN / PWA）の選択肢を検討しましたが、実は状況が違いました。「MulmoClaude にスマホはリモート端末として接続済み。だが MulmoNavi のページを開くと UI が出ず "No records" だけ出る」。

### 原因
ランチャービューは**デスクトップ用のカスタムビュー**でした。スマホのリモートアプリは別の描画契約（`target:"mobile"`・postMessage 経由でデータ取得・`fetch` 全面禁止）で動くため、デスクトップ用ビューは表示されなかったのです。

### 対応
スマホ専用ビュー `phone.html` を新規作成（`schema.json` に `target:"mobile"` で登録）。ただしサンドボックスで Google Maps JS API は読み込めないため、**Google マップアプリのディープリンク**方式にしました。

- 保存済みの行き先は `window.__MC_VIEW.getItems()` で取得して一覧表示。
- 行き先タップ → `https://www.google.com/maps/dir/?api=1&destination=…&travelmode=…` を開き、スマホのネイティブ Google マップがそのまま経路案内。
- 各レコードの移動手段（車/徒歩）を `travelmode` に反映。分類ごとの絵文字（⛰️🏠🕘⭐📍）や、入力欄からの即案内も用意。

「サンドボックスで地図が動かないなら、OS のマップに投げる」という割り切りが、スマホ体験を一気に成立させました。

## フェーズ3 — 会話の破綻を直し、LLM 化への道を作る

### 3-1. 「挨拶したら高速道路の質問が返る」バグ
「こんにちは」と言ったのに「高速道路を使いますか」と返る。調べると根本原因は意図解析 `parseIntent()` にありました。

- 挨拶判定が**完全一致（`^こんにちは$`）**のみ。「はいこんにちは」のように先頭に相づちが付くと判定を外れ、**残った文字が目的地クエリとして扱われジオコード**されていた（＝勝手に目的地化＋トール確認へ突入）。
- さらに調査中、以前入れた正規表現に **`\b?` という無効な量指定子**（V8 でも "Nothing to repeat" 例外→スクリプト全停止）を発見。`node --check` で炙り出して修正。

対応として、先頭のフィラー（はい/うん/ええと/あのー…）を除いた変種でも挨拶・お礼・雑談を判定する `isGreet()` / `isThanks()` / `isChat()` を導入しました。

### 3-2. いったん全体構造を把握する
ここで一度立ち止まり、アプリの構造（UIレイヤー / 状態 `S` / i18n / TTS / STT / 意図解析 / ルート構築 / ターンバイターン案内）を整理。大きな一手の前に地図を持つ、という流れです。

### 3-3. 会話の LLM 化（ハイブリッド2層）— まず調査
「パターンマッチ＋定型文では雑談が成立しない。LLM 化する。ただし**実装より先に調査**」。新設予定の `/api/nav-chat` のバックエンドに何が使えるかを、ホスト側のコードを読んで調べました。

**調査結果:**
- **Claude CLI** を `--print --no-session-persistence --model haiku` で叩けば、**サブスク認証のまま API キー不要**で短文応答に再利用できる（既存の `server/services/translation/llm.ts` や `journal/archivist-cli.ts` が同じ流儀）。ところが**実測で 1ターン 5.7〜11.5 秒**。カーナビの相棒会話には遅すぎる。
- **OpenAI gpt-4o-mini** は `.env` の既存キー流用・低遅延。

コスト判断の末、**OpenAI gpt-4o-mini を採用**。速度が体験を決める用途なので、実測の裏付けが決め手になりました。

### 3-4. 2層ルーティングの設計
- **第1層（遅延ゼロ・確定的）**: stop / start / repeat / mode / category / 高速確認。パターンマッチのまま。
- **第2層（新設）**: 第1層で分類できない発話を `/api/nav-chat` に委譲。

### 3-5. フェーズ2実装 — `/api/nav-chat` 単体
- TTS と同じ **view-token パターン**を踏襲。専用スコープ `aud:"nav-chat"`（`mintNavChatToken` / `requireNavChatToken`）、TTL 1h、レート制限 20/分、入力最大300字。
- システムプロンプトはサーバー側に固定（プロンプトインジェクション対策）。「返答は1文・短く／記号・括弧禁止／操作意図は JSON のみ（set_destination / add_waypoint / stop_nav / start_nav / repeat / play_music）」。
- モデル出力を `parseModelReply()` で解釈し、`{action,...}` か `{reply}` を返す。
- **curl テスト**は稼働セッションを汚さないよう、隔離した Express を一時ポートで立て、`.session-token`（HMAC 署名鍵）から正規トークンを自前生成して叩く方式で実施。401/400/雑談/ETA参照/アクションJSON をすべて実証。

### 3-6. フェーズ3実装 — クライアント統合
- 第1層で会話系に落ちた発話を `navChatReply()` から `/api/nav-chat` へ。失敗時は intent 対応の定型文にフォールバック（会話を止めない）。
- **走行コンテキスト注入** `buildNavContext()`: 現在地の町名（逆ジオコードを45秒キャッシュ）/ 目的地 / 残距離・ETA / 走行モード / 時刻 / 直近3往復の会話。
- LLM のアクションを既存関数へマッピング `handleLLMAction()`（set_destination→検索、add_waypoint→`addWaypointByQuery()`、play_music→スタブ toast など）。
- あなたの追加指定で、few-shot は最小3例、応答待ちの「えっと」フィラーは **800ms 以内に返れば挟まない**、動作確認手順を必ず添える、を反映。

## フェーズ4 — OpenAI 音声（TTS）を載せる

「中断していた OpenAI TTS を、nav-chat の認可基盤に乗せて再開」。調べると **`/api/tts` は過去に構築済みだが未使用**でした（view-token・レート制限・503フォールバックまで配線済み）。サーバーは新規実装不要。

クライアントを **3段構え**で実装:

1. **ナビ定型文** → 初回生成後 **IndexedDB（`mulmonavi-tts`/`clips`）にキャッシュ**。2回目以降は数十msで再生（走行中ゼロ遅延）。
2. **会話応答** → リアルタイム生成（毎回変わるのでキャッシュ対象外 `cache:false`）。
3. **フォールバック** → `/api/tts` 不達・キー未設定（503）・再生失敗時は **Web Speech へ自動フォールバック**。ナビは絶対に止めない。

主要関数: `fetchTts()`（プロキシへ POST → mp3 Blob）、`playBlob()`（`blob:` を再生）、`stopSpeaking()`（割り込み）、キャッシュキー `lang|model|voice|text`。⚙️設定に「OpenAI TTS を使う」トグル（初期ON）＋ボイス選択。nav-chat 応答受信と同時に TTS 生成を開始し、再生開始までの合計遅延をログ出力しました。

## フェーズ5 — 「声が変わらない」— トークン到達問題との長い戦い

ここが本開発最大の難所で、以降くり返し現れます。

### 5-1. 「本当に OpenAI 使ってる?」→ まず可視化
音声が英語訛りで滑らかでない、という疑い。**どのエンジンで鳴ったかを各返答の末尾バッジで可視化**しました（`markEngine()`：`OpenAI` / `OpenAI⚡`（キャッシュ）/ `内蔵`）。あわせて音質を `tts-1-hd` に。正直な注記として「日本語は OpenAI tts-1 より Chrome の Google 日本語音声の方が自然なこともある」ことも共有。

### 5-2. モデル/ボイスを変えても「全く変わらない」→ 5段階調査
「TTS が音声経路に到達していない疑い」を立て、調査手順を具体的に指定。切り分けの結果:

- **サーバーの `/api/tts` は完全に正常**（`.session-token` から自前トークンを作り、稼働中サーバーを直叩き → 200・有効MP3・約1.6秒）。
- **クライアントが到達できず Web Speech に落ちていた**。
- 実機の起動時 `DIAG` ログ（`hashHadMcvt:false / hasTtsToken:false / origin:localhost:5173`）で、**トークンがアプリに渡っていない**と一意に確定。

これは、ランチャーが URL フラグメント（`#mcvt=` / `#mcnav=`）でトークンを渡す仕組みのレース／直開き問題でした。対応:

1. **mintsReady ゲート**: ランチャーのトークン発行が終わるまで起動ボタンを無効化（クリックのユーザー操作コンテキストを失わないよう、await ではなく disabled で）。
2. **アプリ側の案内**: トークン未受領時に画面上部へ「ランチャーから開き直して」バー。
3. **`Cache-Control: no-cache`**: `/artifacts/html` 配信に付与し、旧HTMLキャッシュ事故を予防。
4. 診断用 `TEMP-DIAG` ログは動作確認まで残置。

### 5-3. CSP で `blob:` がブロック
音声再生の `blob:` URL が `default-src 'none'` で弾かれる問題。CSP ビルダー `buildHtmlPreviewCsp()` に `mediaSrc` 引数を追加し、**`/artifacts/html` の配信文書だけに `media-src blob: data:`** を付与（`connect-src 'self'` と同じスコープ方式。印刷/srcdoc プレビューはロック維持）。同一オリジン/インラインのみで外部流出経路は開かない、という安全性を確認。

### 5-4. 後片付け
「えっと」フィラーを廃止（応答待ちは無音でよい）、`TEMP-DIAG` ログも削除。

## フェーズ6 — 多言語の一貫化

「男体山まで」で読み上げが「目的地を『Mount Nantai（Mount…』」と**日英混在**する、という指摘。

### 原因
**Google Maps を言語指定なしでロード**していたため、地名・住所が英語で返っていた。地名の言語は Maps ロード時の `language` で決まり、実行時に変えられない。

### 対応
- Maps ローダに `language` / `region` を `S.lang` から付与（`ja`/`JP` or `en`/`US`）。
- 🌐切替を「永続化＋リロード」に変更 → Maps を新言語で読み直し、UI・案内・検索・TTS・会話・音声認識をすべて追従。
- nav-chat の context に `lang` を追加、システムプロンプトに「必ず context.lang の言語で・混在禁止」を明記。

検証は curl で、日本語モードは全て日本語・英語モードは全て英語になることを実証しました。

## フェーズ7 — 日本語音声品質の追い込み

「OpenAI TTS の日本語が英語訛りで流暢でない」。指示は明快でした:「まず調査 → 全9ボイスの聴き比べを用意 → `gpt-4o-mini-tts` の instructions で日本語ネイティブ発音を指定できるか → 言語連動の自動ボイス切替」。

- **調査**: `/api/tts` は言語ヒント未送。`tts-1-hd` は `instructions` 非対応。**`gpt-4o-mini-tts` は `instructions` 対応**。
- **聴き比べ**: 全9ボイス（gpt-4o-mini-tts＋日本語指示）＋参考を、**自己完結HTML（`data:` 音声を埋め込み）**で生成・提示。CSP の `media-src data:` に適合させて、その場で聴き比べ可能に。
- **サーバー**: `/api/tts` に `instructions` を追加。**`gpt-4o-mini-tts` のときだけ**上流へ転送し、tts-1系へ誤送して 400 になるのを防止。
- **クライアント**: モデル選択（既定 `gpt-4o-mini-tts`）＋**言語別ボイス**（`nav_openai_voice_ja` / `nav_openai_voice_en`。内蔵音声のキーとは別）を導入し、🌐で自動切替。日本語指示 `ttsInstructions()` を付与。

## フェーズ8 — バグ退治（二重発火・遅延・音の重なり）

### 8-1. 二重発火（1発話で nav-chat が2回・二重課金）
ログ証拠（net=3736ms と 3742ms の2本、異なる返答）付きの報告。根本原因は2つ:

- 音声認識 `onresult` が `results[length-1]` を毎回読み、continuous 認識で同一 final に複数回発火。
- 破棄済み recognizer が `onresult` を残したまま `stop()` され、バッファされた final が漏れて2回目発火。

修正: **result index ベースで各 final を一度だけ処理**（`r._done`）、**`killRecog()` で全ハンドラを null にしてから停止**、さらに `handleInput` に**同一発話1.5秒ドロップの保証ガード**（`duplicate input dropped` をログ）。

### 8-2. 遅延の内訳分解
実測で意外な事実が判明:

- nav-chat は典型 0.8〜1.4秒（見えていた3.7秒はコールドのスパイク）。`max_tokens` 80→40 で約 −500ms。
- **`gpt-4o-mini-tts` は tts-1-hd より速い**（full 1.63秒／TTFB 0.99秒 vs tts-1-hd full 4.49秒／TTFB 3.60秒）。「6.3秒」は旧デフォルト `tts-1-hd` の症状で、モデル切替でほぼ解消。
- ストリーミング化は gpt-4o-mini-tts なら不要（nav-chat 約1秒＋TTS 約1.6秒 ≒ 目標3秒以内）。

判断: **gpt-4o-mini-tts の有効化＋`max_tokens` 48** で進め、**ストリーミングは見送り**、プロンプト短縮は会話品質を守るため保留。`max_tokens=48` でも返答・アクションJSONが切れないことを実測確認。

### 8-3. 「同時に AI が喋る」
二重発火とは別の**再生の重なり**。原因は、`tts()` が非同期で、割り込み `stopSpeaking()` は開始時に呼ばれるが実再生は約1.6秒後。2発話がほぼ同時だと両方が生成完了後に再生され重なる。

修正: **TTS を直列キュー化**。`tts()` はキューに積むだけにし、`pumpTts()` が1件ずつ処理。`playBlob()` を「再生開始」ではなく「**再生終了**」で解決するよう変更（`_curRelease` で割り込み時も完了扱い）、`webSpeak()` も await 可能化。新しいユーザー発話で `flushTts()`（進行中を止めキューを空に）。

## フェーズ9 — 会話の自然さ（設計の既定を反転）

根本的な不満:「目的地が勝手に変わる」「自然な会話ができない」。原因は設計そのものでした。

**`parseIntent` の既定の落とし先が「地名検索（ジオコード）」**だったため、挨拶以外で文字が残る発話はすべて行き先として検索され、勝手に目的地化していた（例:「今日は疲れたなあ」→ 適当な地点／実際に "Onigiri Konga" などに化けた）。

### 修正（既定を反転）
- **明示的な行き先マーカー**（`isExplicitDest()`：「〜まで」「〜へ」「案内して」「go to」等）がある時だけ直接ジオコード。
- それ以外はすべて **nav-chat（LLM）に委譲**。LLM が雑談なら会話で返し、地名なら `set_destination` を返す。
- サーバープロンプトに「**地名だけなら set_destination／感情・質問・雑談は会話・勝手に目的地を作らない**」を明記＋例追加。

検証: 「東京駅」「スカイツリー」→ set_destination、「疲れた」「いい天気」「元気?」→ 会話。地名は行き先に、雑談は会話に正しく分離しました。

## フェーズ10 — トークン自己取得 ＆ バージイン（会話の完成）

くり返し現れたトークン到達問題に、恒久的な決着をつけました。要望は「会話にならない。会話できるように。あと**AI の声に割り込んで話せる**ように」。

### 10-1. 会話の恒久対策 — トークン自己取得
主因は依然として「トークンがアプリに届かず nav-chat が定型文に落ちる」。ランチャー経由のフラグメント受け渡し自体が不安定でした。

そこで、アプリが**自分でトークンを取りに行く**方式に:

- 新エンドポイント **`POST /api/nav-view-tokens`** を追加。**same-origin（ループバック）ガードのみ**で bearer 不要（`requireSameOrigin` はローカルホスト由来のオリジンを許可、クロスオリジンは 403）。
- サーバーの認可配線では、この経路を **bearer 免除にするが same-origin 免除にはしない**という細かい分岐を入れた（`isNavViewTokensPath`）。
- アプリは起動時にこれを叩き、tts / nav-chat の両トークンを自己取得。フラグメントがあればそれを優先、なければ自己取得。

検証: 自己取得 → 両トークン発行 → nav-chat/tts とも 200、**別 audience のトークンは 401**（スコープ分離維持）。これで**開き方に関わらず会話も自然音声も確実に動く**ようになりました。

### 10-2. バージイン（割り込み発話）
これまではエコー防止で AI 発話中はマイク入力を無視していました。これを:

- AI 発話中も認識を継続。認識結果が**自分の TTS のエコーか判定**（`isEcho()`：いま読み上げ中の文 `S._botText` との文字重なりで判定）。
- **エコーなら無視、ユーザーの発話なら `flushTts()` で AI を即停止**して処理。
- 読み上げ中の文を `S._botText` に保持し、終了時にクリア。

これで、AI が喋っている最中でも話しかければ AI が止まり、こちらの発言に切り替わる — 人と話すような往復が成立しました。

## 最終アーキテクチャ

```
[音声🎤 / テキスト]
   │  handleInput（二重発火ガード → flushTts で割り込み）
   ▼
第1層 parseIntent（遅延ゼロ・確定的）
   ├ stop / start / repeat / mode / category / 高速確認
   ├ 明示的な行き先マーカー有り → searchDestination（ジオコード）
   └ それ以外 → 第2層へ
        ▼
   /api/nav-chat（OpenAI gpt-4o-mini・view-token・context注入）
        ├ {reply} → 自然な会話
        └ {action} → set_destination / add_waypoint / stop / start / repeat / play_music

読み上げ（直列キュー）: tts → pumpTts（1件ずつ）→ speakOne
   ├ OpenAI TTS（gpt-4o-mini-tts・言語別ボイス・instructions）→ IndexedDBキャッシュ
   └ 失敗/未設定 → Web Speech フォールバック
   ※ バージイン: AI発話中もユーザー発話を受理（エコーは無視）

トークン: 起動時に /api/nav-view-tokens で自己取得（same-origin）
可視化: 返答末尾バッジ（OpenAI / OpenAI⚡ / 内蔵＋理由ツールチップ）
```

## 開発を通じての学び

- **既定値の設計が体験を決める**。「分類できなければ地名検索」という既定が、会話破綻と目的地誤爆の両方の根だった。既定を「会話（LLM）」に反転しただけで自然さが激変した。
- **非同期の割り込みは"開始時"では止められない**。生成に時間のかかる TTS は、直列キュー化で初めて重なりが消えた。
- **トークンは"渡す"より"取りに行く"方が堅牢**。フラグメント受け渡しのレース/直開き問題は、same-origin 自己取得で根絶できた。
- **可視化は最速のデバッグ**。「どのエンジンで鳴ったか」のバッジと理由表示が、原因究明を一気に短縮した。
- **日本語 TTS は英語前提モデルでは限界**。`gpt-4o-mini-tts` ＋ `instructions`（言語指定）＋言語別ボイスで質と速度を両立。
- そして何より、**実機で使い、観測事実（ログ・スクショ・DIAG）を根拠に、根本原因を、段階的に**直していく — この進め方が全体を成功に導いた。
